# Port decisions and evidence

Date: 2026-11-07

## Canon reconciliation

The Java project's declared authority order makes `AUGMENTS.md` the roster canon and the bundled catalog the runtime identity table. This import retains stable catalog IDs and tier order while sourcing displayed Korean name, maximum level, and effect from the canon table. Every catalog name/maximum-level difference remains in `catalog_discrepancy`; three differences were detected. Six entries do not have a Java source file with a literal stable catalog ID. The generic stat service, data contract, and uncommon presentation files are explicitly mapped for `빠른 발`, `버티기`, `긴 팔`, and `물속 작업`; the Shield Grip utility service, tuning, mixin, and contract are explicitly mapped. The roster was regenerated from a clean read-only worktree of Java `origin/main` revision `023e0ca8169da0669faa04a249eedae7169f4f51`; the imported project subtree matches that revision. Baseline canon snapshots remain byte-identical to revision `5962141975b1fea600b0bdb2ae9b697dc7de9cb5`; the latest World Bosses raid-cache and Domination verification documents remain preserved under `docs/java-canon/`. The importer refuses to generate records if its Java worktree differs from fetched `origin/main` within the source project.

Original source files are preserved under `docs/java-canon/`. `docs/augment-roster.json` and `docs/PORT_MATRIX.csv` are generated with `tools/import_canon.py` and include exact canonical effect text, max level, tier, Java source-file hits, interaction-contract line references, and outstanding compatibility/test/port fields. The generic Java stat contract/presentation mapping is explicitly recorded for Quick Feet, Brace, Long Reach, and Underwater Work, whose IDs are not literal in their shared implementation files. Pickup Hand's utility runtime contract and uncommon presentation mapping are also explicitly included because those generic Java resources are its source of truth. Armor Care's durability mixin, success-readability mixin, and survival modifier contract are explicitly mapped.

## Input and UI

The current UI uses built-in server forms and the stable global item-use event: the player uses the matching core for a tier offer, the basic device shows owned augments, and the advanced device handles synthesis. Custom item components V2 are experimental, so the global event preserves the action without that dependency. This avoids undocumented keybind APIs and a 10-key assumption. Forms and item use work through Bedrock's native interaction modes; no key presses are intercepted.

Reference review:

- *Vampire Survivors* presents a small set of upgrade options at a single level-up decision; its documented level-up flow offers three or four choices and upgrades an owned item when selected. We apply the compact multi-choice and upgrade clarity, while retaining the Java core/device economy and not copying its visual style or progression rules. [Level-up reference](https://vampire.survivors.wiki/w/Level_up).
- *Hades* presents three boon choices as a discrete reward decision. This supports showing effect descriptions before commitment. We apply the explicit choice moment, but not its controller-specific layout/art. The 3-choice and in-game description evidence is summarized in a university design analysis with screenshots. [Hades selection analysis (PDF)](https://uu.diva-portal.org/smash/get/diva2%3A1972814/FULLTEXT01.pdf).
- Microsoft's stable `ActionFormData` provides player forms with selectable buttons; `show(player)` returns a selection asynchronously. We use this supported action-form surface as the touch/controller-compatible interaction base. [ActionFormData](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server-ui/actionformdata?view=minecraft-bedrock-stable).

These are design-pattern references, not asset or UI copies. Actual client legibility and touch/controller navigation are NOT_RUN.
