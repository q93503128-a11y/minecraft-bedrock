# API compatibility investigation — 2026-11-05

## Scope and result

This checkpoint records the `날 선 감각`, `정확한 조준`, `질긴 피부`, `가벼운 착지`, and `튼튼한 폐` damage paths plus exploratory movement results against the installed stable Script API and official BDS 1.26.62.1. Java applies these reductions after vanilla mitigation at 2%, 12%, and 15% per level respectively. Bedrock's before-event hook is partial because its mutation occurs earlier in the damage pipeline. Precise Aim can read the projectile and owner, but that owner alone does not preserve the Java distinction between an original player projectile and a player-owned derived projectile.

Classification: **A** means the stable API directly exposes the required event/state operation; **B** means an alternate stable event/state implementation is being used; **C** means a remaining behavior difference is confirmed; **D** means no workable route remains after alternatives are evaluated. A/B describe API routes, not completed ports. `UNASSESSED` means the alternatives or gameplay boundary have not been investigated enough to assign a class.

The API exposes a mutable before-event `damage` field and the damage source, while the after-event damage field is read-only: [EntityHurtBeforeEvent](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityhurtbeforeevent?view=minecraft-bedrock-stable), [EntityHurtAfterEvent](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityhurtafterevent?view=minecraft-bedrock-stable), [EntityDamageCause](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entitydamagecause?view=minecraft-bedrock-stable). The stable API also identifies a projectile's owner and accepts projectile-attributed damage: [EntityProjectileComponent](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityprojectilecomponent?view=minecraft-bedrock-stable), [EntityApplyDamageByProjectileOptions](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entity?view=minecraft-bedrock-stable). Therefore the current event path can apply the server-authoritative scalar but does not reproduce Java's exact mitigation stage or complete root/derived provenance by owner alone.

Both component types inherit `EntityAttributeComponent`. The official reference describes `setCurrentValue` as setting the current value; it does not document persistence across later ticks. I infer that this omission leaves persistence unspecified, and the BDS measurements above are the direct runtime evidence: [EntityAttributeComponent stable API](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityattributecomponent?view=minecraft-bedrock-stable).

An every-tick reapplication attempt was also exercised in the isolated test world; the engine still reported the default player movement value after the tick. This does not establish that every alternative is impossible. The compatibility classification remains **unresolved**: do not label these `C` or `D` until input/velocity methods have been evaluated against actual movement, collision, and mobile controls. No movement code is shipped.

## Reproduction record

- BDS: 1.26.62.1 (`bds-runner.json`), stable production declarations `@minecraft/server` 2.11.0.
- Player attributes exposed both default values and accepted exact multiplied `setCurrentValue` values within the same call.
- First GameTest: Quick Feet level 5 and Webbed Feet level 3 matched their exact base multipliers after one idle tick. After changing both saved levels to 1, both direct values were accepted; after another tick Quick Feet read `0.10000000149011612` instead of `0.1030000015348196`. The test stopped at that assertion, before measuring Webbed Feet after the second tick.
- The experiment failed and was deliberately removed from the passing suite. The add-on does not include these effects, and both roster rows remain `NOT_PORTED`.

A physical arrow launched with `EntityProjectileComponent.shoot` did not damage its intended simulated-player target in the isolated test cell; the attempted physical-hit test was removed and is recorded as failed, not passed. A separate GameTest now sends `Entity.applyDamage` spawned arrows through the stable projectile-damage options, verifies that the production before-event sees each owner, scales 1 damage to 1.04/1.08/1.12/1.16/1.20 at Precise Aim levels 1–5, and leaves both an unaugmented owner and an ownerless projectile at 1. This verifies the production handler and source attribution only; it does not verify flight or collision.
