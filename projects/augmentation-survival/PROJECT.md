## Bedrock target

- Windows client package observed on the development machine: `Microsoft.MinecraftUWP` `1.26.6301.0`; the public in-game version label was not independently checked.
- Minimum engine manifest: `1.26.0`.
- Script APIs: stable `@minecraft/server` 2.11.0 and `@minecraft/server-ui` 2.3.0. No preview module or experimental toggle is declared.
- Supported interfaces: touch, controller focus/navigation, keyboard/mouse through normal item use and forms. No Java-style key binding is assumed.
- Behavior namespace: `augmentation_survival`.
- BP UUID: `365c78a0-d74a-4f42-8e4b-2c147e1dc447`.
- RP UUID: `e92ec459-cc68-452e-92f3-040ff9e602ae`.
- Script-owned data key: `augmentation_survival:levels_v1` on the player entity.
- World support: new or existing worlds, subject to import of both packs. Existing-world migration has not yet been play-tested.

## Build and local checks

From this folder, install the pinned type-check dependencies once, then verify and build:

```powershell
npm ci
npm run verify
```

The pack is generated at `build/AugmentationSurvival-0.1.0.mcaddon`. The build only packages source under `BP/` and `RP/`; it does not replace those files.

## Implemented gameplay slice

- Exact Java-shaped recipe for a common core and both device tiers.
- Using a core presents up to three eligible, unmaxed augments of that core's tier. The server filter enables ten common effects with direct BDS evidence (`날 선 감각`, `정확한 조준`, `질긴 피부`, `빠른 발`, `가벼운 착지`, `튼튼한 폐`, `풍작`, `씨앗 챙기기`, `든든한 한 끼`, and `물갈퀴`) plus fourteen partial uncommon effects (`한 조각 더`, `숨 고르기`, `전리품 챙기기`, `마지막 힘`, `야행성`, `햇빛 체질`, `도구 관리`, `손재주`, `줍는 손`, `물살 타기`, `다급한 발걸음`, `방어구 관리`, `관성 전환`, and `매달리기`) and the rare `광석 눈썰미`. `마지막 힘` adds +10% / +20% / +30% outgoing damage at or below 30% health and stacks additively with `날 선 감각` or `정확한 조준` on tested server damage events. `도구 관리` restores the observed pre-break durability loss on successful player block-break rolls of 5% per level; melee/use durability and automated derived breaks remain outside the event route. `손재주` uses the Java 10% / 20% / 30% chance and whitelist, duplicates one eligible ordinary item after direct player breaks, and remains partial because Bedrock re-rolls the loot table instead of copying the exact native drop; derived harvesting and the pre-Abundance ×2 order remain open. `줍는 손` scans for nearby vanilla item and XP entities every server tick, then moves each item to the nearest eligible augmented player's hitbox center and each XP orb into its upper interior so native inventory and XP award processing is preserved. BDS checks the exact 1.5 / 3.0 / 4.5-block radii, exact XP values (awarded after 3 / 5 / 14 ticks in the final level-1/2/3 run), an outside-radius control, and a shared pickup between two simulated players. The vertical snap and multi-tick XP delay differ from Java's direct call; actual online multiplayer remains unverified. `강건함` remains withheld because the current effect is +4 HP/level against Java's +2; 122 augments remain unported and unofferable. Higher-tier cores with no verified candidates are preserved with a clear message. The selection remains pending until the server confirms the player still has a core; only then is one core removed and the selected level saved.
- Form locks and pending choices carry session tokens. Player leave clears their UI state, and an older delayed form response cannot clear or commit over a later session.
- The basic device opens a paged, read-only inventory of owned augments.
- The advanced device offers the canonical five 3:1 adjacent-tier synthesis transactions. Inputs are checked and consumed on the server; output failure triggers an input rollback.
- Player augment levels are stored in a versioned dynamic property, intended to survive relog/restart through Bedrock entity persistence; persistence across actual reconnects has not yet been tested.
- `강건함` currently uses the stable `health_boost` effect, refreshed after spawn and every 200 ticks from the saved level. BDS measures +4 health points per level, while Java canon specifies +2; this is a known numeric mismatch, not a completed port. The stable health component exposes a read-only effective maximum, so exact parity needs a different supported mechanism.
- The shared server damage handler partially ports `날 선 감각`, `정확한 조준`, `질긴 피부`, `가벼운 착지`, and `튼튼한 폐`. BDS verifies Keen Edge's level 5 synthetic root melee event and Precise Aim's exact owner-attributed projectile curve at levels 1–5 (4% per level). The API route multiplies the latter by 20%, while owner attribution alone cannot distinguish every `ROOT_PROJECTILE` from a player-owned `DERIVED_PROJECTILE`; an actual arrow collision test did not reach its target. Natural fall/drowning, Java's post-mitigation order, delayed-damage provenance, and client acquisition remain unverified, so each effect remains partial.
- `풍작` uses the stable player-break after-event and applies Java's 8% per-level chance (up to 40%) to mature wheat, carrots, potatoes, and beetroot, spawning one ordinary crop product. `씨앗 챙기기` independently rolls 15% per level (up to 45%) and adds the crop's mapped planting item. Java performs the Bumper Crop roll before the Seed Saver roll; BDS verifies both exact curves, their separate roll order, simultaneous success, maturity checks, and all four product/planting-item mappings with synthetic event data. Live block-breaking, Silk Touch/tool-specific drops, and Java external crops remain unverified. Both compatibility rows are partial, not complete.
- `한 조각 더` follows Java's 5% / 10% / 15% per-level ore bonus: the production handler recognizes vanilla ore IDs and exposed ore tags, uses the stable pre-break permutation/tool to recalculate the first ordinary loot, clones one item, and spawns it after the roll. BDS verifies all level boundaries, Silk Touch and Fortune outputs, non-ore and unmineable-tool rejection, plus live `playerBreakBlock` delivery with a SimulatedPlayer. The live event test does not assert a real survival proc; external ores/tags, client play, multiplayer, and derived-break routing for future `굴파기` remain open. See the compatibility report.
- `광석 눈썰미` uses the canonical rare 6 / 8 / 10-block spherical radius and scans every 10 ticks. The production BP checks loaded blocks only, detects vanilla ore IDs and Bedrock ore tags, and draws owner-only cyan custom particle markers around exposed ore. BDS verifies that the production selection transaction consumes one rare core and stores level 1, then checks each saved level/radius, water exposure, a fully buried control, and that marker calls target only the owning player. Since stable Script API has no block collision-shape getter, exposure uses air/liquid plus a list of common collisionless vanilla block IDs; custom/unlisted blocks and the exact continuous Java outline can differ. Visual readability on PC, mobile, and controller has not been checked.
- `도구 관리` keeps Java's 5% per-level roll and maximum level 5 on the stable player-break route: the production BP captures the selected slot before a break, reads the before/after durability snapshots, then restores the pre-break durability after a successful roll. If the last durability point broke the tool, it returns the captured stack only while that same slot is still empty. BDS 1.26.62.1 verifies all chance boundaries and runs 40 level-5 simulated stone breaks through the production handler; that run saved 6 durability events and spent durability on the other 34. This is a partial route: melee and other item-use durability are not observed, the stable Script API does not expose Java's `DataComponents.TOOL` marker, and automated derived block breaks are not routed. The Java interaction contract requires automatic mining/harvest to inherit durability behavior, so add those shared routes when their break engine is ported.
- `방어구 관리` keeps Java's independent 5% per-level chance for each equipped armor piece, capped at 25%. BDS 1.26.62.1 verifies the production entityHurt before/after route across 20 ordinary and 20 near-break hits (14/80 ordinary and 18/80 near-break saved outcomes in the latest full-suite level-5 run; the separate probe recorded 17/80 and 20/80), exact chance-helper boundaries, and an unowned control. Stable API cannot cancel the exact armor durability sub-event, so Bedrock restores the same still-equipped stack after native damage; a broken item or an empty/different-type slot is skipped; same-type stack identity is not exposed. Same-tick repeated hits, Unbreaking combinations, cross-add-on durability writes, reconnect/restart, and online multiplayer remain unverified. Class B / partial; enabled for uncommon offers. See [the implementation report](docs/ARMOR_CARE_IMPLEMENTATION_2026-11-07.md).
- `전리품 챙기기` rolls once at Java's 5% / 10% / 15% chance per level on a player-attributed non-player mob death, then spawns a second bundle from the mob loot table while filtering all six augment-core IDs. BDS 1.26.62.1 checks exact chance boundaries, confirms the stable loot-table API can return cow beef for a dead entity, and tests player attribution, eligible-stack copying, and core exclusion with a deterministic injected loot bundle. An isolated native re-roll returned an empty bundle, so non-empty bonus generation and equality with original drops remain unverified. Unlike Java's copied final stacks, Bedrock's stable `entityDie` does not expose the original loot consumer; looting variants, external boss profiles, companion exclusions, and Loot Scoop × Abundance stacking also remain open.
- `든든한 한 끼` adds Java's 8% / 16% / 24% of the food's vanilla saturation gain. The production handler subscribes to stable `itemCompleteUse`, reads exact data-driven food values where exposed, and measures vanilla food's saturation change from adjacent server ticks. BDS 1.26.62.1 verifies actual cooked-beef consumption at all three levels and the food saturation cap. The stable API reference describes this event as chargeable-item completion, and only cooked beef has been tested for this route; see [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md) before treating other food/engine combinations as proven.
- `물갈퀴` adds Java's 10% / 20% / 30% swim-speed bonus only while in water. The production handler applies the stable `minecraft:underwater_movement` attribute from the saved level and restores its default value out of water. BDS 1.26.62.1 verifies the production handler's actual swimming velocity at all three levels and the reset; coexistence with other add-ons modifying the same attribute and real-client feel remain untested. See [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md).
- The shared movement reconciler applies `빠른 발` at exact +3% per level (five levels), `야행성` at +5% per level only at night, and `햇빛 체질` at +4% per level only during daytime. BDS verifies all levels, day/night activation and deactivation, and additive Quick Feet + conditional movement values; the server logic uses Java's 13,000-tick boundary. These remain partial ports: Nocturnal's separate mining-speed bonus and Sun Affinity's separate natural-regeneration interval reduction are not implemented. Direct player-visible walking speed, mobile/controller feel, and stacking with every other movement augment still need review. See [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md).
- `낚시 감각` remains disabled and unported. Java scales the private vanilla hook timer by 10% / 20% / 30%; the current stable API exposes rod-use events and the hook entity but no bite event or timer setter. The BDS probe confirmed that the spawned hook exposes only its generic projectile component among the queried components. A Lure or custom-rod replacement would change vanilla timing/item behavior and would not preserve Java's percentage rule. See [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md).
- `숨 오래 참기` remains disabled and unported. Java's oxygen attribute yields 10% / 20% / 30% longer underwater breath duration. Stable `minecraft:breathable.totalSupply` is read-only; `airSupply` is marked pre-release in the official reference, omitted from stable API declarations, and absent from the tested BDS player component. Water Breathing would not preserve the percentage reduction. See [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md).
- `추위 적응` remains disabled and unported. Java reduces positive freeze-buildup ticks by 15% / 30% / 45% with fractional tick credit, retaining vanilla freeze and thaw behavior. Stable API exposes freezing damage but no player freeze counter; reducing damage would change the effect rather than delay buildup. See [the compatibility report](docs/API_COMPATIBILITY_2026-11-06.md).

- 기수 has a server-side partial speed implementation for sole control-seat riders: BDS verifies +10% / +20% / +30% mount movement values and restoration after dismount. Java also increases jump strength; stable Script API exposes no numeric jump-strength writer, so 기수 remains disabled as a core candidate. The exact limits and diagnostics are in [the Rider implementation report](docs/RIDER_IMPLEMENTATION_2026-11-07.md).
